This page describes the Engine 2.0 Spine runtime API. See [Using in the Editor](/en/docs/graphics/2D/spine/editor) for editor asset names and import UI; editor integration migrates separately.

## Install and configure

Application code uses objects from `@galacean/engine-spine`. Install the backend matching your assets and pass one runtime instance when creating the engine. Import `engine-spine` before engine creation so its loader receives this configuration:

```typescript
import { WebGLEngine } from "@galacean/engine";
import "@galacean/engine-spine";
import { Spine38Runtime } from "@galacean/engine-spine-core-3.8";

const engine = await WebGLEngine.create({
  canvas: "canvas",
  spine: new Spine38Runtime()
});
```

Editors or applications can register another version later without clearing existing resources:

```typescript
import { registerSpineRuntime } from "@galacean/engine-spine";
import { Spine42Runtime } from "@galacean/engine-spine-core-4.2";

registerSpineRuntime(engine, new Spine42Runtime());
```

Each engine has its own version map. Loading selects a registered backend by the asset's export major/minor version. Existing resources, cached results and playback keep their original backend; adding 4.2 does not replace 3.8. Re-registering the same instance is allowed, but a different instance for an already registered version is rejected. Reuse the backend instance when revisiting a version. An application using one version installs only that backend. Backend imports do not register it automatically, and missing versions fail explicitly without downloading another backend.

## Load and instantiate

Here, `engine` is an existing engine instance with an active scene. Configure a scene camera to cover the character's position.

```typescript
import { SpineAnimationRenderer, SpineResource } from "@galacean/engine-spine";

const resource = await engine.resourceManager.load<SpineResource>({
  url: "/spine/character.skel",
  type: "Spine"
});
const entity = resource.instantiate();
engine.sceneManager.activeScene!.addRootEntity(entity);
const renderer = entity.getComponent(SpineAnimationRenderer)!;
renderer.state.setAnimation(0, "idle", true);
```

Replace the animation, skin, slot and attachment names in these examples with names from your asset.

| Input           | Loader selection                                                            |
| --------------- | --------------------------------------------------------------------------- |
| `.skel`         | Selects the Spine loader automatically; explicit `type: "Spine"` also works |
| `.json`, `.bin` | Requires explicit `type: "Spine"`                                           |

The loader accepts Spine JSON and binary skeleton data and detects the encoding from the content. The extension selects the loader; it does not guarantee binary content.

For a single URL, an explicit atlas dependency takes precedence. Otherwise, the loader derives a sibling `.atlas` URL. For example, `character.skel?v=2` resolves to `character.atlas`, without inheriting the skeleton query. Use `urls` to specify atlas or texture addresses:

```typescript
const explicitResource = await engine.resourceManager.load<SpineResource>({
  type: "Spine",
  urls: ["/spine/character.json?v=2", "/spine/character.atlas?v=3", "/spine/body.png?v=4", "/spine/weapon.png?v=5"]
});
```

Usually, skeleton and atlas URLs are enough: textures are loaded from atlas page names. Explicit texture URLs should match those names. Renamed textures that cannot be matched by page name use the URL at the corresponding page index. Requests retain the full URLs.

`SpineResource` shares skeleton data, skins, mixing configuration and textures. Each `instantiate()` creates an independent pose and playback state. The following examples use the `resource` and `renderer` above.

## Arrange playback and control time

`renderer.state` is this instance's `SpineAnimationState`. Use `setAnimation` to replace an animation on a track and `addAnimation` to queue one. The engine advances playback automatically; application code does not call `update`.

```typescript
resource.stateData.defaultMix = 0.2;
resource.stateData.setMix("attack", "idle", 0.15);

const state = renderer.state;
state.setAnimation(0, "attack", false);
state.addAnimation(0, "idle", true, 0);
```

Tracks can play concurrently. They are applied from lower to higher indices, allowing higher tracks to override or blend with lower tracks. Mix durations belong to the resource and affect all its instances.

`setAnimation` and `addAnimation` return a `SpineTrackEntry` representing one playback entry. It controls that entry's mixing weight, time and callbacks; it is not a reusable animation asset.

```typescript
renderer.timeScale = 0.5; // Scale animation and skeleton time, including 4.2 physics.
const previousTimeScale = renderer.timeScale;
renderer.timeScale = 0; // Pause time; pose application and rendering continue.
renderer.timeScale = previousTimeScale;

const entry = renderer.state.getCurrent(0);
if (entry) entry.trackTime = 1.5; // Apply this animation time on the next update.
```

`state.timeScale` and `entry.timeScale` provide additional animation scaling without scaling skeleton physics time. Use `renderer.timeScale` for ordinary speed and pause controls. Seeking an animation does not reconstruct physics history.

Use queues for known sequences and `entry.listener` for notifications belonging to one playback:

```typescript
const attack = renderer.state.setAnimation(0, "attack", false);
attack.listener = {
  complete(entry) {
    console.log("Playback completed", entry.animation?.name);
  },
  event(entry, event) {
    console.log("Authored event", event.data.name, event.stringValue);
  }
};
```

Use `state.addListener(listener)` for state-wide notifications and `removeListener` to remove it. Looping animations emit `complete` each loop. An entry becomes invalid after its `dispose` callback returns; authored event values are snapshots that may be retained. Command callbacks are synchronous, so a listener assigned after a command returns does not receive a `start` event that has already happened.

## Pose update signals

Use the renderer's signals to work with the current frame's pose:

| Signal             | Timing and purpose                                                                            |
| ------------------ | --------------------------------------------------------------------------------------------- |
| `onBeforeApply`    | After time advances, before animation application; prepare the base pose.                     |
| `onUpdateLocal`    | After animation application, before world transforms and constraints; edit local bone values. |
| `onUpdateWorld`    | After a preliminary world-transform solve; adjust local values using evaluated world values.  |
| `onUpdateComplete` | After the final solve, before geometry generation; read the final pose for following objects. |

```typescript
const aim = (source: SpineAnimationRenderer) => {
  const head = source.skeleton.findBone("head");
  if (head) head.rotation += 15;
};
renderer.onUpdateLocal.on(aim);
// Remove when no longer needed:
renderer.onUpdateLocal.off(aim);
```

Signals run synchronously in the listed order, even with `timeScale = 0`. A listener on `onUpdateWorld` enables an additional pose solve; 4.2 physics still advances only once. `onUpdateComplete` does not re-solve subsequent local bone edits. Bone world values are in skeleton space and need the entity's world transform to position scene objects.

Spine updates after scripts' `onLateUpdate`; use these signals for precise pose timing. Listeners remain on the renderer when its resource changes, so access its current skeleton in callbacks. Renderer destruction clears listeners. Signal cloning remaps component/method bindings and does not copy function listeners.

## Skins, bones and slots

`renderer.skeleton` is this instance's `SpineSkeleton`. After switching skins, restore slots to their setup pose to select the new skin's setup attachments:

```typescript
renderer.skeleton.setSkinByName("winter");
renderer.skeleton.setSlotsToSetupPose();
```

Create a composite skin through the resource and add skins from that same resource:

```typescript
const outfit = resource.createSkin("outfit");
for (const name of ["base", "hair/brown", "clothes/winter"]) {
  const skin = resource.skeletonData.findSkin(name);
  if (skin) outfit.addSkin(skin);
}
renderer.skeleton.setSkin(outfit);
renderer.skeleton.setSlotsToSetupPose();
```

Skins belong to a resource and may be shared by its instances. Cross-resource composition is rejected. `findBone(name)` and `findSlot(name)` return stable instance objects, or `null` for a missing name.

```typescript
const weapon = renderer.skeleton.findSlot("weapon");
if (weapon) {
  weapon.setAttachment("sword");
  weapon.setAttachment(null); // Hide the attachment.
  weapon.setToSetupPose(); // Restore the setup configuration.
}
```

Attachment names are resolved from the current skin, falling back to the default skin. `skeleton.slots` remains in setup order regardless of animated draw order. Bone local transforms are editable, but animation-controlled values are written again when animations are applied.

The public API supports skin composition and attachment selection by name. Native `TextureAtlas`, `RegionAttachment` and `MeshAttachment` objects are internal. Older examples that load an extra atlas and directly modify native attachments do not apply to this API.

## Materials and alpha encoding

Characters within an Engine share a default `SpineMaterial`. Use `setMaterial(material)` to assign the default or `getInstanceMaterial()` to obtain an independent copy. `setMaterial(0, material)` addresses the default material; numeric indices do not identify slots or internal draw batches.

For a slot override, pass a `SpineSlot` from this character:

```typescript
import { SpineMaterial } from "@galacean/engine-spine";

const material = new SpineMaterial(engine);
const weapon = renderer.skeleton.findSlot("weapon");
if (weapon) {
  renderer.setMaterial(weapon, material);
  renderer.setMaterial(weapon, null); // Remove the override and use the default.
}
```

`new SpineMaterial(engine, customShader)` supports custom shaders. Enable `renderer.tintBlack` for two-color tint. A custom shader must consume Spine's vertex layout and batch texture/blend inputs. When using the supplied blend factors, tint in linear space and multiply the final RGB by the final alpha. See the [Spine package material contract](https://github.com/galacean/engine/blob/dev/2.0/packages/spine/README.md#materials) for the inputs.

Spine uses the engine's linear rendering workflow. Export **Straight Alpha** textures: disable **Premultiply alpha** and enable **Bleed** in Spine's Texture Packer. Bleed fills transparent pixels with neighboring colors without changing alpha, reducing dark edges during filtering. The shader premultiplies its final linear output for blending.

The loader rejects atlas pages marked `pma: true` and textures with `isSRGBColorSpace: false`. Ordinary images use sRGB sampling by default; enable sRGB when exporting `.tex` or compressed textures as well. Generate compression and mipmaps from the straight-alpha image with color bleed. Textures share the existing resource loading and restoration path, without GPU readback or conversion textures.

Older atlases without `pma` are assumed to be straight alpha. Re-export legacy PMA images; merely changing the atlas flag does not convert the image. There is no alpha-mode override or renderer-level `premultipliedAlpha` switch.

## Physics and resource unbinding

The 4.2 backend supports Spine physics constraints; 3.8 explicitly reports the capability as unsupported. Check support before accessing it:

```typescript
const physics = renderer.physics;
if (physics?.supported) {
  for (const constraint of physics.value.physicsConstraints) constraint.reset();
}
```

Set `renderer.resource = null` to clear the binding. Do not access `state` or `skeleton` while unbound. Rebinding creates new instance state and clears slot material overrides. Do not continue controlling playback through objects from a destroyed entity.
